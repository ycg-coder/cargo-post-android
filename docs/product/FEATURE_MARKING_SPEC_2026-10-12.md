读法（原文开头三行）：
- 冗余：`是（预留）` = 当前实验/比赛阶段可不实现，为未来预留；`否` = 当前核心功能。
- 入口：功能在 APP 或后台中的位置。
- 对接：数据/服务来源或去向。

⚠ 三条已知的"不能照抄"的地方（照抄就会与本项目既有决定打架，逐条都在 DECISION_LOG 里有实测）：
1. `一（二）天气/限行提醒 = 是（预留）` —— **App 司机端已经做了**（D-076 续六：`DriverWeatherTip` + 工作台那一栏，
   并且按角色分了两份说法）。这里的"预留"不构成本轮把它撤掉的理由。
2. `一（九）/二（五）预约` 一族 —— 用户的硬规则是**不提供网上预约乘车**（乘客侧），
   而"快件预约揽收"是另一件事；凡落到"预约乘车"的条目一律按既有服务边界处理，不新造乘车预约。
3. `二（三）在线支付` 与 `二（八）支付` 标了预留，`三（十一）对账结算` 标了核心 ——
   钱包/支付侧的代码就绪但缺商户资质（D-076 之前的实测），所以"配置留空 = 模拟模式"，
   不能因为这份表写了"否"就当成已可上线的真实支付。
4. `一（二）绩效/公告/联系调度/车队` 里的**公告**这一格已在 2026-10-12 晚间落到司机端工作台（D-080：
   `Repo.notices()` → `ui/driver/DriverNotices.kt` 判定 → 工作台 `item(key = "notice")`），
   本机后端实测 `GET /app-api/transport/notice/list` 回 `{"code":0,"data":[]}` —— 通路是真的、库里当前 0 条，
   所以这一格现在正确地"不出现"。同一行里的绩效/车队仍按原表理解，别因为公告做了就把整行念成已交付。
